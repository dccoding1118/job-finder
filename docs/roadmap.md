# 產品 Roadmap — job-finder：從個人 MVP 到台灣職場求職 Copilot

MVP 的功能規格見 [PRD](PRD.md)；本文件回答四個問題：**現在的 MVP 能用在哪裡、未來目標長什麼樣子、怎麼逐步擴展上去、這件事在市場上值不值得做**。

## 1. 願景（終局）

一個台灣職場的 **AI 求職 Copilot（Micro-SaaS）**：使用者填一次去識別化 Profile，系統持續掃描各求職平台，主動送上「值得投的職缺 ＋ 可直接用的客製化投遞素材」，並追蹤投遞成效、回頭校準偏好——把求職從「人找職缺」翻轉成「職缺找人、人只做決策」。

差異化定位（承 MVP 三原則）：**Zero-PII**（資料最小化，天然合規優勢）、**Human-in-the-Loop**（不代投，避開平台 ToS 與誤投風險）、**重質不重量**（評分閾值＋雙 Agent 審查，反海投）。

## 2. 現在的 MVP 是什麼、能用在哪裡

| 用途 | 說明 |
|---|---|
| 自用求職加速器 | 開發者本人 2026 求職期間每日實際使用：省下掃職缺與寫信的時間，並以真實投遞成效驗證評分與生成品質 |
| AI 落地代表作品 | Multi-Agent 協作、雙層過濾、防幻覺審查、冪等 pipeline——面試與作品集的可展示實例 |
| 產品核心的驗證場 | MVP 的資料流（抓取→過濾→評分→生成→回饋）就是未來產品的核心引擎；單人真實使用即最早的 product validation |

MVP 架構中為擴展預留的縫：Source adapter（加平台不動核心）、Runner 抽象（CLI 換直串 API 只換實作）、store 隔離（SQLite 換 PostgreSQL 不動業務層）、雙軸狀態機與事件流（天然支撐多用戶成效統計）。

## 3. 階段規劃

### S0 — 個人 MVP（現在，對應 PRD 交付計畫 B0–B6）

- **目標**：自己每天用得起來；完成「抓取→評分→生成→手動投遞→狀態追蹤」閉環。
- **形態**：單人單機（GCP VM）、CLI ＋ localhost API ＋ Chrome 原生 Side Panel（含單一 Profile 全頁編輯器與 104 半被動擷取）、SQLite、headless CLI LLM；Profile 仍以版控外 YAML 為真相。
- **退出標準**：連續兩週日常使用；三來源皆通（Yourator/Cake 全自動、104 插件半被動）；投遞 ≥20 筆由本系統產出的求職信。

### S1 — 自用強化（求職期間持續迭代）

- **目標**：從「能用」到「好用」，並開始累積成效數據。
- **關鍵項**：
  - 反向校準閉環實際運轉（interview 事件 → Profile 建議）。
  - 主動通知：每日高分職缺摘要推送（Email / LINE / Discord 擇一）。
  - 成效統計頁：投遞數、回應率、各來源/分數帶的轉換率——同時是未來產品的賣點素材。
  - 評分與生成品質迭代（以真實投遞結果當 eval）。
  - 匯入去識別化履歷並產生 Profile 草稿，經使用者檢查與確認後才寫入；支援多 Profile 的建立、切換與個別媒合歸屬。
  - **深入評估（按需）**：推薦職缺提供「深入評估」動作，才產出優缺點、機會分析，並查詢公司與職缺評論等外部即時評價。與求職信同屬按需觸發——每筆職缺的例行評分維持五維＋短理由，把較貴的分析留給使用者真的在考慮的少數職缺。此功能定案前，`ScoreResult` 不擴充 pros/cons 欄位。
- **架構演進**：無重大變更；驗證「事件流→統計」的資料模型。

### S2 — 私測 Alpha（少量真人試用，單租戶部署）

- **目標**：驗證「別人也能用」——Profile 建置體驗與產出品質對非本人是否成立。
- **關鍵項**：
  - e2e Web UI 第一版：將本機 extension 的 Profile 表單與求職流程遷入具登入的 Web 介面；Profile 改為租戶資料，不再依賴本機 YAML。
  - 實名登入（Google OAuth）；每使用者一份 Profile 與資料隔離。
  - 部署上雲：容器化、每租戶獨立實例（沿用 SQLite 亦可），最小維運。
  - LLM 改直串 API（Runner 換實作）：多用戶下 CLI 訂閱模式不成立；開始量測每用戶 token 成本。
- **退出標準**：3–5 位試用者走完閉環並願意持續用；每用戶月度 LLM 成本可估算。

### S3 — 公開 Micro-SaaS

- **目標**：公開服務＋收費，驗證願付價格。
- **關鍵項**：
  - 多租戶架構：SQLite → PostgreSQL；任務佇列與 per-tenant rate limit；爬蟲集中化（全體共用抓取池，媒合各自 Profile——成本從 O(用戶) 降為 O(平台)）。
  - 計費：訂閱制或「生成信件額度」制；LLM 成本控管（批次、模型分級、快取）。
  - 爬蟲合規與供給策略：評估平台官方 API / 合作授權 / 使用者自帶資料的混合路線（**最大商業風險，S3 前須定案**；MVP 的 104 插件路線即「使用者自帶資料」的雛形）。
  - Landing 官網＋產品說明＋費用方案頁。
- **退出標準**：付費用戶 >0 且單位經濟（客單價 vs LLM＋基建成本）為正。

### S4 — 擴展（選項池，依 S3 學習取捨）

- 更多來源：LinkedIn（合作/授權路線）、1111（插件路線）、獵頭/內推管道。
- 投遞素材擴展：履歷客製化重排（PDF 生成）、面試準備 Agent（依 JD 生成考題與話術）。
- 成效數據飛輪：跨用戶匿名統計回饋評分模型（哪類 Profile×JD 組合真的拿到面試）。
- B 端變體：企業/獵頭側的反向媒合介面。

## 4. 產品化運作流程與目標架構（S2→S3 形態）

### 4.1 運作流程（用戶旅程 × 元件）

| # | 流程 | 元件 | 說明 |
|---|---|---|---|
| 1 | 註冊 / 登入（Google OAuth） | **Web**（container service） | 建立帳號；通知 Email 存於帳號層（見 §4.4） |
| 2 | 建立/編輯 Profile、設定偏好與通知 | **Web** → DB | 承接 S0 extension 表單的業務欄位，加入帳號與租戶資料；PII 檢核在送出時執行 |
| 3 | 每日排程執行 pipeline | **Scheduler** → **Pipeline Job**（container job） | 即現在 MVP 的 `jobfinder run` 打包成 job：抓取 → 初篩 → 評分，逐租戶媒合；求職信依用戶要求生成 |
| 4 | 推薦通知寄送 | **Pipeline Job** 尾端 → **Email 服務**（SES/SendGrid 類） | 高分職缺摘要；點擊導回站內檢閱與決定是否生成求職信 |
| 5 | 用戶回站操作 | **Web** | 備選職缺（`scored`，未達閾值）、推薦職缺（`shortlisted`/`letter_ready`）、要求生成求職信、求職信檢閱複製、投遞狀態回報、run 運作歷程、設定配置 |
| 6 | 回饋閉環 | **Pipeline Job**（校準）＋ **Web**（確認） | 狀態事件累積 → 校準建議 → 用戶站內確認套用 |

### 4.2 目標架構圖

```
                        OAuth
                          ▲
   Browser ◄────────► ┌───┴──────────────┐
                      │ Web              │  Profile/偏好/狀態/設定 CRUD
                      │ (container svc)  │  清單/對照/複製/歷程檢視
                      └───────┬──────────┘
                              │
 Scheduler(每日) ─┐   ┌───────▼──────────┐
                  ├──►│ DB (PostgreSQL)  │  帳號層｜媒合層（分離，見 §4.4）
 手動觸發(Web) ───┘   └───────▲──────────┘
                              │
                      ┌───────┴──────────┐      ┌────────────┐
                      │ Pipeline Job     │─────►│ LLM API    │
                      │ (container job)  │─────►│ Email 服務 │
                      │ ＝MVP run 的容器化│      └────────────┘
                      └───────┬──────────┘
                              │ S3 拆出
                      ┌───────▼──────────┐
                      │ 集中抓取池 worker │  全體共用抓取，媒合各自 Profile
                      └──────────────────┘
```

- **S2（單租戶 Alpha）**：Web ＋ Pipeline Job 兩個部署單元即可，抓取仍在 job 內。
- **S3（多租戶 SaaS）**：抓取池拆為獨立 worker（成本 O(平台) 而非 O(用戶)），job 之間以任務佇列派工。

### 4.3 MVP 模組 → 產品元件對應

| MVP 模組（現在） | 產品化元件（未來） | 演進動作 |
|---|---|---|
| `api`（localhost JSON API）＋ Side Panel／Profile editor | Web container | 將 Job／Run／Profile 操作遷入 Web，並加 OAuth、租戶資料隔離、設定頁與通知偏好 |
| `pipeline`＋`crawler`＋`agents`（`jobfinder run`） | Pipeline Job container | 打包容器、改吃租戶參數；Runner 換直串 LLM API 實作 |
| `store`（SQLite） | PostgreSQL | 介面不變、換 driver；加租戶維度 |
| systemd timer | Cloud Scheduler | 觸發語意相同（每日 one-shot、冪等） |
| （無） | Email 通知服務 | S1 先做單機簡版（自用推送），S2 接正式 Email 服務 |
| （無） | 帳號/身分模組 | S2 新增 |

### 4.4 Zero-PII 邊界的產品化調整

| 層 | 內容 | PII 政策 |
|---|---|---|
| 帳號層 | 登入身分、通知 Email、計費資訊 | 必要 PII，僅此層持有，與媒合資料實體分離（不同 schema/表，Job 寄信時才查詢） |
| 媒合層 | Profile、JD、評分、求職信、狀態事件 | 維持 Zero-PII：無姓名/Email/電話/校名/公司名；求職信仍佔位符落款，由用戶投遞時自行替換 |

此分離讓「求職資料」在資料外洩、供應商存取、LLM 傳輸等場景都不含身分資訊——是產品的合規賣點，非只是工程潔癖。

## 5. 跨階段演進總表

| 面向 | S0–S1（自用） | S2（Alpha） | S3（SaaS） |
|---|---|---|---|
| 使用者 | 本人 | 3–5 試用者 | 公開付費 |
| Profile | extension 表單編輯單一 YAML 真相 | Web 表單＋每租戶資料 | Web 表單＋多 Profile／範本 |
| 資料庫 | SQLite | SQLite（每租戶） | PostgreSQL 多租戶 |
| LLM | headless CLI（訂閱內） | 直串 API | 直串 API＋成本工程 |
| 爬蟲 | 本機 per-user | 單租戶實例 | 集中抓取池＋合規供給 |
| 部署 | VM ＋ systemd timer | 容器單租戶 | 容器多租戶＋排程服務（見 [deploy](deploy.md)） |
| 登入 | 無（localhost） | Google OAuth | OAuth＋計費身分 |
| UI | Chrome 原生 Side Panel | e2e UI 第一版 | 完整 e2e＋Landing |

## 6. 市場判斷與商業化風險

本節是 S2/S3 決策的參照：**需求真實、技術可行，但台灣把它放大成大生意的結構性障礙同樣真實**。定性結論——這是一門可行的小而美工具生意，不是 venture-scale 題目。

### 6.1 需求為何成立

| 論點 | 依據 |
|---|---|
| 既有平台的通知是條件訂閱，不是語意媒合 | 104 通知本質是關鍵字/地區/薪資的結構化匹配，precision 低（實際體感：數日才出現一個想投的職缺）。以 LLM 對 JD 全文 × Profile 全文做多維評分，精準度是另一個量級 |
| 利益結構與求職者一致 | 平台收入來自企業端曝光，推薦引擎讓求職者「多看多投」符合平台利益；本產品的利益是「精準少投」。此差異動到平台的商業模式，不是它加一層 LLM 就能抹平 |
| 「重質不重量」有數據支撐 | 業界統計：精準投遞 11–20 封的面試率約 9.25%，海投 100+ 僅約 2.58% |
| 賽道已被國際驗證 | 美國的 Jobright、Simplify、Teal 即此形態（AI 媒合＋履歷客製＋投遞追蹤），有真實 C 端付費市場（如 Simplify+ 約 $39.99/月）。台灣尚無本土化對應品 |

同時要認清：104 已在推 AI 推薦（宣稱提高面試機會 3.2 倍）——方向被平台方認證有價值，但也意味著 **LLM 媒合終將成為 table stakes**，光有「用 LLM 評分」不構成長期差異化。

### 6.2 台灣沒人做的理由（風險清單）

| 障礙 | 說明 | 本專案的對應 |
|---|---|---|
| 市場小＋需求間歇 | 求職是數年一次、每次二至三個月的事 → 高流失、LTV 低、須持續重新獲客。這是求職 C 端產品的通病 | pivot 選項 (a)：轉為在職者的長期「市場守望」訂閱（§6.4） |
| C 端付費意願弱 | 104 / Cake / Yourator 一律向企業端收費並非巧合；台灣求職者的付費習慣顯著弱於美國 | 定價須壓在低價帶（§6.3）；或 pivot 選項 (b)：轉 B 端 |
| 資料供給的法律風險 | 商業化爬取有實際訴訟前例風險 | 已列為 S3 門檻：合規供給策略未定案前不做公開推廣（§3 S3、§7） |
| 護城河薄 | prompt 層人人能抄；平台方握有資料與流量 | 護城河候選：**跨平台聚合**（104＋Cake＋Yourator＋LinkedIn 單一入口，平台彼此做不到）、**回饋閉環數據**（哪類 Profile×JD 真的拿到面試）、**Zero-PII 信任定位** |

### 6.3 分級判斷

| 層級 | 判斷 |
|---|---|
| 自用＋作品集 | 價值確定，不受任何市場風險影響——這已足以支撐 S0–S1 的全部投入 |
| Micro-SaaS 副業 | 可行，天花板低。合理想像：台灣 tech 求職者 NT$199–399/月、活躍期 2–3 個月；達到千位數付費用戶即年營收百萬台幣級的副業 |
| 放大 | 需 pivot（§6.4）；維持現形態難以突破需求間歇與 C 端付費意願兩道天花板 |

### 6.4 Pivot 選項（S4 選項池的商業側）

- **(a) 市場守望訂閱**：面向**被動求職者**（在職者長期讓 agent 盯市場）的低價常訂閱，解掉「需求間歇→高流失」的結構問題。
- **(b) B 端變體**：獵頭／企業側的反向精準媒合——台灣的付費方本來就在 B 端。

### 6.5 對階段決策的含義

S1 的成效統計即是市場驗證的關鍵數據：自用三個月後，「本系統推薦 → 投遞 → 面試」的轉換率相對既有平台通知的體感落差，就是**是否進入 S2 的最誠實依據**。

外部數據來源：104「AI 創新百強」公開說明；Jobright / Simplify / Teal 之公開定價與產品評測；求職投遞量與面試率之業界統計。

## 7. 原則性取捨

- **每一階段都要先是「自己願意每天用的工具」**：S1 做不到好用，就不進 S2。
- **不提前為 SaaS 付架構稅**：MVP 只投資「介面縫」（adapter/Runner/store），不預建多租戶。
- **合規先於規模**：爬蟲供給策略未定案前不做公開推廣（S3 門檻）。
