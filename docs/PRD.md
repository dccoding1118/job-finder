# PRD — job-finder（Anonymous AI Job Matcher，MVP）

## 1. 背景與定位

job-finder 是一個基於 Go 與 LLM Agent 的「反向求職媒合與客製化求職信生成工具」：每日自動抓取台灣求職平台職缺（反爬防護平台如 104 則以瀏覽器插件於使用者瀏覽時半被動擷取），以雙層過濾（本地規則 + Agent 多維評分）篩出高匹配職缺並標示判定；使用者對推薦職缺決定投遞時才按下生成，由雙 Agent 管線（起草 + 審查）產出防幻覺的客製化求職信，最後在 Chrome Side Panel 檢閱、複製、手動投遞並追蹤狀態。

- **使用情境**：MVP 僅供開發者本人使用（單人單機），同時作為「AI 落地」代表作品。
- **保留擴充**：未來可演進為台灣職場 Micro-SaaS（e2e UI、實名登入、收費），MVP 不做，但架構不阻擋。產品化路線見 [產品 Roadmap](roadmap.md)。

### 核心原則

| 原則 | 意涵 |
|---|---|
| Zero-PII | 資料庫與版控內容嚴禁儲存姓名、Email、電話、身分證字號、就讀學校名稱；求職信落款一律使用 `[你的姓名]`、`[你的聯絡方式]` 佔位符 |
| Human-in-the-Loop | 系統邊界停在「產出求職信」；求職信只在使用者對推薦職缺表達投遞意願後才生成；投遞動作由使用者於外部平台手動執行；Profile 校準建議須人工確認後才套用 |
| Quality over Quantity | 規則初篩 + Agent 評分閾值淘汰不匹配職缺；Reviewer Agent 淘汰幻覺與空泛內容，寧缺勿濫 |
| 判定即時可見 | 職缺的判定（不適合／推薦／不推薦／待補全文）一律在使用者當下所在的介面呈現：清單頁以既有欄位快速判定並就地標記，Side Panel 呈現目前內頁的完整評分 |

## 2. 名詞與實體

| 實體 | 說明 | 儲存位置 |
|---|---|---|
| Profile | 去識別化的專業履歷（技能、年資、經歷、成就、求職偏好） | `profile.yaml`（版控外，人可編修的單一真相） |
| Source | 職缺來源平台：Yourator / Cake（全自動 adapter）、104（瀏覽器插件半被動擷取） | 程式碼 + 設定檔 |
| Job | 抓取到的職缺（JD、公司資訊、薪資、連結、來源識別） | SQLite |
| MatchScore | 單一 Job 的五維評分、加權總分與推薦理由 | SQLite |
| CoverLetter | 審查通過的客製化求職信（含審查歷程） | SQLite |
| StatusEvent | 職缺處理狀態與投遞狀態的每次變更紀錄（反向校準的資料來源） | SQLite |
| Run | 一輪 pipeline 執行的紀錄（時間、各階段筆數、錯誤） | SQLite |

## 3. 狀態與所有權模型

Job 有兩條正交的狀態軸，擁有權不同：

### 3.1 處理狀態 `process_state`（系統擁有）

| 狀態 | 意義 |
|---|---|
| `discovered` | 插件列表收割入庫，僅列表可見欄位（無 JD 全文）；欄位可用的初篩規則已過＝待看清單成員，待使用者點開內頁補全文 |
| `new` | 已有 JD 全文，尚未初篩 |
| `filtered_out` | 被條件篩選淘汰＝**不適合**（終態，保留供稽核） |
| `queued` | 通過初篩，待 Agent 評分 |
| `scored` | 已評分，總分 < 閾值＝**不推薦**（終態） |
| `shortlisted` | 已評分且總分 ≥ 閾值＝**推薦**；停留於此等待使用者決定是否投遞，系統不主動生成求職信 |
| `letter_requested` | 使用者已對推薦職缺要求生成求職信，待管線處理 |
| `letter_ready` | 求職信通過審查，可供投遞（終態，轉由投遞狀態軸接手） |
| `letter_failed` | 求職信經重寫上限仍未過審；使用者可再次要求生成 |

### 3.2 投遞狀態 `apply_state`（使用者擁有，僅 `letter_ready` 的 Job 適用）

| 狀態 | 對應需求用語 |
|---|---|
| `pending` | 待處理（預設） |
| `applied` | 已投遞 |
| `interview` | 一面（含後續面試輪次） |
| `offer` | 發放 Offer |
| `ghosted` | 無聲卡 |
| `dropped` | 主動放棄 |

### 3.3 欄位擁有權

| 欄位群 | 擁有者 |
|---|---|
| Job 原始內容、`process_state`、MatchScore、CoverLetter | 系統（pipeline） |
| 求職信生成的**觸發時機**（`shortlisted` → `letter_requested`、`letter_failed` → `letter_requested`） | 使用者（經 UI 操作）；轉換本身仍由 store 執行 |
| `apply_state` 及其變更事件 | 使用者（經 UI 操作） |
| Profile 內容 | 使用者（系統僅提出校準「建議」） |
| Profile 儲存命令 | 使用者（僅明確按下儲存時執行）；系統負責驗證、原子寫入與切換 active snapshot |
| 既有職缺重新處理命令 | 使用者（僅明確按下更新過時評分時執行）；系統負責重新篩選與排入評分 |

## 4. 功能需求

### R1 匿名 Profile

- **R1.1** 以 `profile.yaml` 承載去識別化履歷與求職條件：技能（分類與熟練度）、年資、學歷（學位層級與領域，無校名）、經歷（角色、產業、年資區間、職責與量化成就，無公司名——以「雲端代理商」「國際商銀」等類型描述）、期望薪資區間、地點、遠端意願、P1/P2/P3 方向關鍵字、產業避開項目，以及職稱／工作內容／公司排除與必要關鍵字。
- **R1.2** 提供 PII 檢核指令：以版控外的 denylist（姓名、Email、電話、校名、公司名等）掃描 profile 與產出的求職信，命中即報錯。
- **R1.3** 反向校準：當 `interview` 事件累計達門檻（設定檔 `calibration.min_interviews`，預設 5），可執行校準指令，由 Agent 萃取成功案例 JD 特徵並產出 Profile 偏好調整「建議 diff」，由使用者確認後手動套用（不自動改寫）。
- **R1.4** Chrome extension 提供完整 Profile 建立、檢視與編輯表單；結構化 JSON 只作 API 傳輸，`profile.yaml` 仍是唯一真相，不存入 SQLite 或 extension storage。
- **R1.5** Profile 不自動儲存。使用者明確送出後，後端必須先完成 strict schema 驗證與 PII 檢核，再以 owner-only 權限原子替換；失敗時磁碟檔與 active Profile 均不得改變。
- **R1.6** Profile 讀取回傳檔案 ETag，儲存強制使用 `If-Match`；外部修改造成衝突時拒絕覆蓋。語意內容以 canonical 結構計算 `profile_revision`，相同內容的重複儲存不得重新入隊或增加 Agent 成本。
- **R1.7** filter、score、letter 與相關 Agent 呼叫記錄實際使用的 `profile_revision`。Profile 語意改變後，新擷取職缺立即使用新 revision，既有職缺保留原 revision 並導出 stale；只有使用者明確要求更新過時評分時，尚未進入求職信流程的既有職缺才依新 revision 重新篩選並視結果重新評分。`letter_requested`、`letter_ready`、`letter_failed`、既有 Letter 與投遞歷史不自動改動。
- **R1.8** Profile 缺少或無效時，`serve` 仍可啟動 Profile 編輯與讀取型 API；抓取、capture 處理與 worker 暫停，直到有效 Profile 儲存並啟用。

### R2 來源層（多來源 adapter 與合規供給）

- **R2.1** 來源以統一 adapter 介面掛載，新增平台不動核心流程。
- **R2.2** 全自動來源第一批 **Yourator**（公開 JSON API），第二批 **Cake**（搜尋頁 SSR 解析）。
- **R2.3** 去重與變更偵測：以 `(source, external_id)` 唯一鍵去重；以內容雜湊偵測 JD 變更，變更時重置為 `new` 重新評估。
- **R2.4** 禮貌抓取：請求間隨機延遲、限制每輪頁數、失敗退避；單一來源失敗不影響其他來源。
- **R2.5** **104 為半被動來源**：不做伺服器端自動抓取（全站反爬防護，見 R2.7 零繞過原則）；由瀏覽器插件於使用者瀏覽時擷取（R9），經 capture API 進入同一 pipeline。
- **R2.6** 搜尋條件（不做全量抓取）：各來源的搜尋 queries 由 Profile `preferences.directions[].keywords`（P1/P2/P3 方向關鍵字）自動展開生成——Profile 是關鍵字的單一真相，關鍵字以技能詞為主（平台職務類別與制式職稱不可靠）；設定檔可覆寫或增補，並提供指令檢視展開結果與生成 104 巡邏 URL。
- **R2.7** 合規邊界（各來源共用）：只碰免登入公開頁、遵守 robots.txt、**零繞過**（遇人機驗證／加密參數即停）、內容不重散布；公開 repo 不含反爬繞過程式碼，測試 fixture 內容一律合成。

### R3 條件篩選

與 R2.6 的分工：搜尋條件負責擴大合適職缺的涵蓋範圍；條件篩選負責排除平台搜尋難以表達的限制。平台搜尋結果常含贊助與模糊命中職缺，故抓回後仍需本地過濾。

- **R3.1** 依 Profile 的求職條件淘汰明顯不符職缺，不耗用 LLM：排除關鍵字（職稱/工作內容）、必要關鍵字（任一命中）、可接受地點、薪資下限與公司黑名單。
- **R3.2** 淘汰者標記 `filtered_out` 並記錄命中規則，供調參稽核。
- **R3.3** partial 職缺（`discovered`，無 JD 全文）只套用欄位可用的規則；需要內文的規則於補全文後執行——不以標題錯殺分類錯置的職缺。
- **R3.4** 條件篩選不耗用 LLM 且不需 JD 全文的特性，使它可作為**清單頁的快速判定**：插件收割列表項目時同步得出判定並回傳，供頁面就地標記（R9.1）。此路徑的延遲需求是「使用者仍在該頁面時看得到結果」，不等待評分或求職信等 LLM 階段。

### R4 AI 多維評分

- **R4.1** 五維評分（各 0–100）與權重：

| # | 維度 | 權重 |
|---|---|---|
| 1 | 硬技能覆蓋率（JD 要求技能 vs Profile 技能） | 30% |
| 2 | 領域與場景重疊度（產業、系統型態、雲平台生態） | 15% |
| 3 | 年資與職級匹配度 | 15% |
| 4 | 工作條件契合度（薪資、地點、遠端/混合、工作型態） | 20% |
| 5 | 方向契合度（命中 P1 雲端架構 / P2 AI 落地 / P3 Java 雲原生的程度與敘事空間） | 20% |

- **R4.2** 加權總分由程式計算（非 Agent 自算）；總分 ≥ **75** 進入 `shortlisted`，等待使用者決定是否要求生成求職信。
- **R4.3** 每筆評分附 100 字內「推薦/不推薦理由」。
- **R4.4** 評分、信件起草與信件審查可分別設定主要與備援 CLI Runner；使用者在本機調整設定後，下一輪執行即採用新路由。

### R5 雙 Agent 求職信管線（Drafter–Reviewer）

- **R5.0** **按需生成**：達閾值的推薦職缺（`shortlisted`）不自動進入求職信管線；使用者於 Side Panel 檢閱評分後，對想投遞的職缺按下「產生求職信」，Job 才轉入 `letter_requested` 由管線處理。理由：求職信是全流程最耗 token 的階段，且系統不支援自動投遞，未經使用者決定的求職信沒有使用價值。`letter_failed` 的職缺同樣由使用者再次要求才重跑。
- **R5.1** Drafter：比對 Profile 與 JD 撰寫精煉求職信；強調量化實績；落款強制 `[你的姓名]`、`[你的聯絡方式]` 佔位符。
- **R5.2** Reviewer：審查草稿——凡 Profile 無根據的技能/經歷（幻覺）、過度空泛形容詞、誇大宣稱，判定 `revise`（附具體問題退回重寫）或直接刪改後 `approve`。
- **R5.3** 重寫上限 2 輪；仍不過審則標記 `letter_failed` 留待人工。
- **R5.4** 程式端防線：求職信中出現的技術詞須存在於 Profile 技能集 ∪ JD 內文（詞表比對），落款佔位符缺失即擋下——不完全依賴 LLM 審查。

### R6 Chrome Side Panel 儀表板

- **R6.1** 職缺清單：按 Match Score 排序，可依 `process_state` / `apply_state` / 來源篩選；每筆顯示判定（不適合／推薦／不推薦／待補全文／待評分）。
- **R6.2** 「目前職缺」以窄幅單欄依序呈現判定、總分／命中條件、理由、五維評分、JD 內容與審查通過的求職信；尚未生成求職信的推薦職缺於此顯示生成入口。
- **R6.3** 一鍵複製求職信至剪貼簿。
- **R6.4** 投遞狀態變更（按鈕/下拉，MVP 不做拖曳看板），每次變更寫入 StatusEvent。
- **R6.5** 手動觸發一輪抓取與檢視 Run 歷史（含該輪職缺的現行判定分布）。
- **R6.6** Chrome 原生 Side Panel 是唯一日常操作入口，toolbar action 直接開啟；固定提供「目前職缺、待看、推薦、系統」四個頁籤。Options 可設定 localhost API endpoint 與 token。API 僅監聽 loopback；遠端部署時，extension 透過 SSH local forward 存取本機轉送埠。
- **R6.7** 待看頁籤列出 `discovered` 職缺（職稱、公司、薪資、原始連結），供使用者逐筆點開由 content script 補全文。
- **R6.8** 求職信生成入口：推薦職缺（`shortlisted`）提供「產生求職信」動作，送出後顯示處理中，完成時呈現求職信或未過審結果；`letter_failed` 提供再次生成。
- **R6.9** Side Panel 支援淺色與深色主題；切換不得清除目前頁籤、職缺或操作狀態。主題選擇可持久化，JD、求職信與 token 不因 UI 快取而另存副本。
- **R6.10** 「系統」頁依序呈現連線與設定、Profile、自動與手動批次、批次歷程群組；可開啟 Options 與 Profile 全頁編輯器、查看每日 08:30（Asia/Taipei）排程，並手動抓取或更新過時評分。Profile 編輯草稿只存在頁面記憶體；衝突時保留草稿並要求重新載入，不提供強制覆蓋。
- **R6.11** 職缺總分與五維分數在 UI 四捨五入為整數。已有評分的職缺顯示評分所屬 Profile revision；與 active revision 相同顯示綠色「最新」，不同或無法證明則顯示黃色「待重評」。

### R7 排程與執行

- **R7.0** 抓取與處理分別驅動：抓取（全自動來源爬取）由排程成批觸發；初篩→評分→生成由**常駐 worker** 持續消化資料庫中的待處理職缺。排程抓取、CLI 與插件擷取三個入口寫入的職缺共用同一條消化路徑，不因來源不同而有等待差異。
- **R7.1** `jobfinder run` 執行一輪抓取，抓完即退出，不等待任何 LLM 階段。全系統**冪等**：狀態即進度，中斷後重啟從殘留狀態續作，不重複計費已完成的 Agent 呼叫。
- **R7.2** 每日一輪抓取由 systemd user timer 觸發（台北時間）；Side Panel 與 CLI 皆可手動觸發抓取。worker 隨常駐服務啟動，無需觸發。
- **R7.3** LLM 呼叫序列化並套用最小間隔（rate limit），評分/生成筆數有**每日上限**（設定檔控制，台北時間日界重置）。上限用盡時職缺留待隔日，使用者的要求不會遺失。

### R8 觀測與稽核

- **R8.1** 每輪 Run 記錄該次**抓取**的事實（時間、觸發方式、使用的搜尋條件、取得與新建筆數、錯誤摘要）。該輪職缺的判定分布於檢視時即時查詢導出，不存為抓取當下的快照——worker 非同步消化，快照必然過期。插件擷取的職缺由使用者自行導覽產生，不屬於任何 Run。
- **R8.2** Agent 原始輸入輸出留存（本地檔案或 DB），供除錯與作品集展示；內容不得含 PII。

### R9 瀏覽器插件（104 半被動擷取與即時判定）

- **R9.1** 列表收割與快速判定：於 104 搜尋結果頁與職缺通知頁，自動擷取使用者已載入的職缺項目（職稱、公司、薪資、地區、連結）送 capture API。API 對每筆同步回傳判定，插件就地標記於該項目上：
  - **已存在於資料庫的職缺**直接回傳其現行判定與總分，不重跑任何階段——使用者一眼看出哪些已評為推薦或不適合。
  - **新職缺**入庫為 `discovered`，並以欄位可用的條件篩選（R3.3、R3.4）即時判定：命中淘汰規則者標記為**不適合**（`filtered_out`，紅底或排除圖示，附命中的規則）；通過者標記為**待補全文**，成為待看清單成員。
  - 此路徑不呼叫 LLM、不算分數；清單欄位不足以支撐五維評分，強行評分既不準也拖慢回應。
- **R9.2** 內頁擷取與完整評估：於職缺內頁自動擷取 JD 全文送 capture API，建立完整 JD 資料並**同步**執行條件篩選，評分則交由常駐 worker 非同步進行（R7.0）。Side Panel 的「目前職缺」依此呈現：
  - 條件篩選淘汰者標記為**不適合**並附命中的規則——該路徑不含 LLM，**同步即得**，不需等待。
  - 已有現行評分者直接顯示快取結果（判定、五維分數與理由），不重複計費。
  - 通過篩選、待評分者顯示**評分中**，由 Side Panel 低頻輪詢本機 API 至結果出現；使用者關閉分頁不影響後端消化，重開時直接命中快取。
  - 求職信不在此階段生成（R5.0）。
- **R9.3** 巡邏動線：`queries urls` 指令由 Profile 生成 104 巡邏搜尋 URL；使用者亦可於 104 以同組條件註冊職缺通知，通知 email 僅作提醒，入口為站內通知頁（以 R9.1 收割）。
- **R9.4** 合規邊界：插件只處理使用者本人瀏覽器已載入的頁面；不背景開分頁、不批次自動抓取、不繞過任何防護。
- **R9.5** 待看清單消化：Side Panel 的待看頁籤提供逐筆開啟原始職缺的使用者動作。
- **R9.6** 判定用語一致：清單標記與 Side Panel 對同一筆 Job 顯示同一組判定，且由同一份 API 回應導出，不各自實作判定規則。

## 5. 完整流程

職缺有三條入口，匯流到同一套判定與同一個資料庫；求職信是所有入口之後、由使用者按需觸發的獨立階段。

Profile 是所有處理入口的共同前置條件。Profile 缺少或無效時，系統只提供 setup 與讀取功能；有效儲存後立即啟用新 snapshot，但不改動既有 Job revision。每個 filter／score／letter 工作開始時固定取得一份 snapshot 與 revision，工作途中不換版；既有職缺由使用者明確要求後才切換 revision 並重新處理。

```
【入口 A：批次抓取（systemd timer / Side Panel / CLI 觸發）】
  → fetch    ：全自動 Source（Yourator/Cake）抓取 → upsert Job（去重、變更偵測）→ new
  → filter   ：條件篩選 → filtered_out ∣ queued
  → score    ：Scorer 五維評分 → 程式計算加權總分 → <75 ⇒ scored ∣ ≥75 ⇒ shortlisted

【入口 B：104 清單頁（使用者瀏覽 ＋ 插件，隨時發生）】       ※ 快速判定，不呼叫 LLM
  → 列表收割 ：搜尋頁/通知頁 → capture API
               ├ 已存在於 DB ⇒ 直接回傳現行判定與總分（不重跑）
               └ 新職缺 ⇒ discovered → 欄位可用的條件篩選
                          → 命中 ⇒ filtered_out（不適合）∣ 通過 ⇒ 待看清單
  → 就地標記 ：不適合（紅底/圖示）∣ 推薦 ∣ 不推薦 ∣ 待補全文

【入口 C：104 職缺內頁（使用者點開）】                      ※ 完整 JD ⇒ 完整判定
  → 內頁擷取 ：capture API → 補入 JD 全文（discovered ⇒ new，或新建 new）
  → 條件篩選 → filtered_out ∣ queued
  → 排入評分 ：通過篩選者由常駐 worker 非同步評分 → <75 ⇒ scored ∣ ≥75 ⇒ shortlisted
  → Side Panel「目前職缺」：待處理時顯示評分中；完成後顯示五維分數與理由（已有現行評分則直接顯示快取）

【使用者於 Side Panel（推薦職缺的決策點）】
  → 檢閱清單與對照（判定、五維分數、理由、JD）
  → 對想投遞的推薦職缺按「產生求職信」⇒ letter_requested
       → letter：Drafter 起草 → Reviewer 審查 →（≤2 輪重寫）
                 → 過審 ⇒ letter_ready ∣ 不過 ⇒ letter_failed（可再次要求）
  → 一鍵複製 → 外部平台手動投遞 → 標記 apply_state
  → interview 累計達門檻 ⇒ 可跑校準 → 產出 Profile 建議 diff → 人工套用
```

## 6. MVP 不包含（Out of Scope）

- 104／1111 等反爬防護平台的伺服器端自動抓取，以及任何形式的反爬繞過（headless 瀏覽器偽裝、驗證碼破解、加密參數逆向）——不因技術可行而納入。
- 插件背景自動開分頁批次抓取。
- SMTP 寄信、求職平台自動填表/自動投遞。
- PDF 履歷排版與生成（以文字求職信輔助既有靜態履歷）。
- 多使用者、登入、收費、Landing page（保留為未來擴充）。
- 匯入 PDF／Word／Markdown 履歷並自動填寫 Profile、多 Profile／多履歷切換，以及可還原的 Profile 歷史版本。
- 以新 Profile 自動重生或覆蓋已核准求職信、改寫投遞狀態或投遞事件。
- 拖曳式看板 UI（以按鈕變更狀態替代）。
