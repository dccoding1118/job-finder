# PRD — job-finder（Anonymous AI Job Matcher，MVP）

## 1. 背景與定位

job-finder 是一個基於 Go 與 LLM Agent 的「反向求職媒合與客製化求職信生成工具」：每日自動抓取台灣求職平台職缺（搜尋路徑受人機驗證保護的平台如 104、Cake 則以瀏覽器插件於使用者瀏覽時半被動擷取），以兩關判定（硬規則篩選決定適合與否、軟規則評分決定推不推薦）篩出高匹配職缺並標示判定；使用者對推薦職缺決定投遞時才按下生成，由雙 Agent 管線（起草 + 審查）產出防幻覺的客製化求職信，最後在 Chrome Side Panel 檢閱、複製、手動投遞並追蹤狀態。

- **使用情境**：MVP 僅供開發者本人使用（單人單機），同時作為「AI 落地」代表作品。
- **保留擴充**：未來可演進為台灣職場 Micro-SaaS（e2e UI、實名登入、收費），MVP 不做，但架構不阻擋。產品化路線見 [產品 Roadmap](roadmap.md)。

### 核心原則

| 原則 | 意涵 |
|---|---|
| Zero-PII | 資料庫與版控內容嚴禁儲存姓名、Email、電話、身分證字號、就讀學校名稱；求職信落款一律使用 `[你的姓名]`、`[你的聯絡方式]` 佔位符 |
| Human-in-the-Loop | 系統邊界停在「產出求職信」；求職信只在使用者對推薦職缺表達投遞意願後才生成；投遞動作由使用者於外部平台手動執行；Profile 校準建議須人工確認後才套用 |
| Quality over Quantity | 硬規則篩選淘汰條件不符職缺 + 軟規則評分閾值淘汰不匹配職缺；Reviewer Agent 淘汰幻覺與空泛內容，寧缺勿濫 |
| 資訊不足不判死 | 硬規則篩選缺乏判定所需資訊時絕不判為不適合——寧可多評一筆，也不漏掉機會。清單摘要有無從判定的條件歸「待看」等補全文；全文 JD 只要沒有任何條件不符，即照常進「待評分」 |
| 判定即時可見 | 職缺的判定（不適合／推薦／不推薦／待看／待評分）一律在使用者當下所在的介面呈現：清單頁以既有欄位快速判定並就地標記，Side Panel 呈現目前內頁的完整篩選與評分結果 |

## 2. 名詞與實體

| 實體 | 說明 | 儲存位置 |
|---|---|---|
| Profile | 去識別化的專業履歷（技能、年資、經歷、成就、求職偏好） | `profile.yaml`（版控外，人可編修的單一真相） |
| Source | 職缺來源平台：Yourator（全自動 adapter）、104 / Cake（瀏覽器插件半被動擷取） | 程式碼 + 設定檔 |
| JobGroup | 跨來源指向同一個實際職缺的 Job 群組；群組內只有一筆 canonical 承載評分、求職信與投遞狀態 | SQLite |
| Job | 抓取到的職缺（JD、公司資訊、薪資、連結、來源識別） | SQLite |
| FilterResult | 單一 Job 的硬規則逐條判定（`pass`／`fail`／`unknown`）與 JD 條件拆解 | SQLite |
| MatchScore | 單一 Job 的四維評分、加權總分與推薦理由 | SQLite |
| CoverLetter | 審查通過的客製化求職信（含審查歷程） | SQLite |
| StatusEvent | 職缺處理狀態與投遞狀態的每次變更紀錄（反向校準的資料來源） | SQLite |
| Run | 一輪 pipeline 執行的紀錄（時間、各階段筆數、錯誤） | SQLite |

## 3. 狀態與所有權模型

Job 有兩條正交的狀態軸，擁有權不同：

### 3.1 處理狀態 `process_state`（系統擁有）

| 狀態 | 意義 |
|---|---|
| `discovered` | 插件列表收割入庫，僅列表可見欄位（無 JD 全文）；欄位可用的硬規則已過＝待看清單成員，待使用者點開內頁補全文 |
| `new` | 已有 JD 全文，尚未篩選 |
| `filtered_out` | 硬規則有任一條判 `fail`＝**不適合**（終態，保留供稽核） |
| `new` | 有 JD 全文、篩選尚未完成（程式與 LLM 兩段）＝**篩選中** |
| `queued` | 通過硬規則篩選，待 Agent 評分 |
| `scored` | 已評分，總分 < 閾值＝**不推薦**（終態） |
| `shortlisted` | 已評分且總分 ≥ 閾值＝**推薦**；停留於此等待使用者決定是否投遞，系統不主動生成求職信 |
| `letter_requested` | 使用者已對推薦職缺要求生成求職信，待管線處理 |
| `letter_ready` | 求職信通過審查，可供投遞（終態，轉由投遞狀態軸接手） |
| `letter_failed` | 求職信經重寫上限仍未過審；使用者可再次要求生成 |
| `merged` | 經判定為其他 Job 的重複刊登，成為該群組的 alias（終態）；不評分、不生成、不出現在清單，可由使用者取消合併還原 |

### 3.2 投遞狀態 `apply_state`（使用者擁有，僅 `letter_ready` 的 Job 適用）

| 狀態 | 對應需求用語 |
|---|---|
| `pending` | 待處理（預設） |
| `applied` | 已投遞 |
| `interview` | 一面（含後續面試輪次） |
| `offer` | 發放 Offer |
| `ghosted` | 無聲卡 |
| `dropped` | 主動放棄 |

### 3.3 欄位擁有權

| 欄位群 | 擁有者 |
|---|---|
| Job 原始內容、`process_state`、MatchScore、CoverLetter | 系統（pipeline） |
| 求職信生成的**觸發時機**（`shortlisted` → `letter_requested`、`letter_failed` → `letter_requested`） | 使用者（經 UI 操作）；轉換本身仍由 store 執行 |
| `apply_state` 及其變更事件 | 使用者（經 UI 操作） |
| Profile 內容 | 使用者（系統僅提出校準「建議」） |
| Profile 儲存命令 | 使用者（僅明確按下儲存時執行）；系統負責驗證、原子寫入與切換 active snapshot |
| 既有職缺重新處理命令 | 使用者（僅明確按下更新過時評分時執行）；系統負責重新篩選與排入評分 |

## 4. 功能需求

### R1 匿名 Profile

- **R1.1** 以 `profile.yaml` 承載去識別化履歷與求職條件，依用途分成六個區段：`search`（搜尋用方向關鍵字）、`requirements`（硬規則：薪資下限、可接受地區、遠端意願、工作型態、排除產業／職稱／內文／公司）、`intents`（軟規則：目標薪資、想做與不想做的工作內容、期許產業）、`experiences`（一份工作一列：產業、年資、是否管理職、技能，以及供求職信取材的角色與量化成就，無公司名——以「雲端代理商」「國際商銀」等類型描述）、`qualifications`（學歷、技能熟練度、證照、語言，無校名）、`honesty_bounds`（防幻覺誠實邊界）。年資與產業年資由系統從 `experiences` 加總物化，使用者不重複填寫。
- **R1.2** 提供 PII 檢核指令：以版控外的 denylist（姓名、Email、電話、校名、公司名等）掃描 profile 與產出的求職信，命中即報錯。
- **R1.3** 反向校準（S1 範圍，MVP 不交付）：當 `interview` 事件累計達門檻（設定檔 `calibration.min_interviews`，預設 5），由 Agent 萃取成功案例 JD 特徵並產出 `search`／`requirements`／`intents` 的調整「建議 diff」（不得建議修改履歷事實），由使用者確認後手動套用（不自動改寫）。入口為 Side Panel，不提供 CLI 指令；規劃見 [roadmap](roadmap.md) S1。
- **R1.4** Chrome extension 提供完整 Profile 建立、檢視與編輯表單；結構化 JSON 只作 API 傳輸，`profile.yaml` 仍是唯一真相，不存入 SQLite 或 extension storage。
- **R1.5** Profile 不自動儲存。使用者明確送出後，後端必須先完成 strict schema 驗證與 PII 檢核，再以 owner-only 權限原子替換；失敗時磁碟檔與 active Profile 均不得改變。
- **R1.6** Profile 讀取回傳檔案 ETag，儲存強制使用 `If-Match`；外部修改造成衝突時拒絕覆蓋。語意內容以 canonical 結構計算兩個 revision：`filter_revision` 涵蓋硬規則欄位、`score_revision` 涵蓋軟規則欄位；相同內容的重複儲存不得重新入隊或增加 Agent 成本。只影響搜尋或求職信取材的欄位不改變任一 revision。
- **R1.7** filter、score、letter 與相關 Agent 呼叫記錄實際使用的 revision。Profile 語意改變後，新擷取職缺立即使用新 revision，既有職缺保留原 revision 並導出 stale；只有使用者明確要求更新過時評分時，尚未進入求職信流程的既有職缺才重新處理，且重跑範圍依變更的 revision 決定——`filter_revision` 變更者全部重篩、通過者再重評；只有 `score_revision` 變更者只重評、不重篩。`letter_requested`、`letter_ready`、`letter_failed`、既有 Letter 與投遞歷史不自動改動。
- **R1.8** Profile 缺少或無效時，`serve` 仍可啟動 Profile 編輯與讀取型 API；抓取、capture 處理與 worker 暫停，直到有效 Profile 儲存並啟用。

### R2 來源層（多來源 adapter 與合規供給）

- **R2.1** 來源以統一 adapter 介面掛載，新增平台不動核心流程。
- **R2.2** 全自動來源為 **Yourator**（公開 JSON API）。可全自動抓取的平台是例外而非常態——多數台灣平台的搜尋路徑在人機驗證之後，一律走 R2.5 的半被動路線。
- **R2.3** 同來源去重與變更偵測：以 `(source, external_id)` 唯一鍵去重；以內容雜湊偵測 JD 變更，變更時重置為 `new` 重新評估。
- **R2.4** 禮貌抓取：請求間隨機延遲、限制每輪頁數、失敗退避；單一來源失敗不影響其他來源。
- **R2.5** **104 與 Cake 為半被動來源**：不做伺服器端自動抓取；由瀏覽器插件於使用者瀏覽時擷取（R9），經 capture API 進入同一 pipeline。兩者受阻的環節不同但結論相同——104 全站在人機驗證後；Cake 內容開放，但帶任何搜尋條件的請求一律被人機驗證擋下，伺服器端無法以求職條件挑出目標職缺（見 R2.7 零繞過原則）。
- **R2.6** 搜尋條件（不做全量抓取）：各來源的搜尋 queries 由 Profile `search.directions[].keywords`（P1/P2/P3 方向關鍵字）自動展開生成——Profile 是關鍵字的單一真相，關鍵字以技能詞為主（平台職務類別與制式職稱不可靠）；設定檔可覆寫或增補，並提供指令檢視展開結果。半被動來源的搜尋條件由使用者在該平台自行設定，系統不代為組裝搜尋連結。
- **R2.7** 合規邊界（各來源共用）：只碰免登入公開頁、遵守 robots.txt、**零繞過**（遇人機驗證／加密參數即停）、內容不重散布；公開 repo 不含反爬繞過程式碼，測試 fixture 內容一律合成。平台自身前端使用的搜尋 API 金鑰即使可從頁面取得，也不得繞過其人機驗證直接呼叫。
- **R2.8** 跨來源同一職缺合併：同一職缺常同時刊登於多個來源。以程式規則辨識（公司名正規化分群＋職稱正規化比對＋地區相容性，不呼叫 LLM）：高信心者自動合併為同一群組，只有 canonical 那一筆評分、生成求職信與承載投遞狀態，其餘轉入 `merged`；相似但不確定者登記為「疑似重複」，由使用者在 Side Panel 一鍵合併或忽略。已有評分、求職信或投遞歷史者不自動合併。合併可由使用者取消還原。

### R3 硬規則篩選（適合與否）

與 R2.6 的分工：搜尋條件負責擴大合適職缺的涵蓋範圍；硬規則篩選負責排除平台搜尋難以表達的限制。平台搜尋結果常含贊助與模糊命中職缺，故抓回後仍需本地判定。硬規則決定的是「適合與否」，不是分數——條件不符即淘汰，不以扣分表達。

- **R3.1** 結構化條件由程式比對 Profile 的 `requirements`，不耗用 LLM：地區、遠端意願、工作型態、薪資下限、排除產業、職稱／內文／公司排除關鍵字。
- **R3.2** 語意條件由 Filter Agent 比對 Profile 的 `qualifications` 與 `experiences`：學歷與科系、必備技能、必要證照、必要語言、必要產業經驗。年資、管理年資與產業年資的加總與比較一律由程式以物化的加總值執行，Agent 只做語意對應（JD 的要求對應到哪些產業、要求幾年）。
- **R3.3** 篩選關先產出 JD 的條件拆解：每條標記為必備或加分，並標示選言（「A 或 B」滿足任一即通過）。加分條件不列入篩選，只供評分關的加分維度重用；此拆解與逐條判定一併保存，兩關不各自重解。
- **R3.4** 每條判定為 `pass`／`fail`／`unknown`，彙總時綜合全部條件。任一 `fail` ⇒ `filtered_out`（不適合），不論同時有多少 `unknown`；無 `fail` 時，清單摘要維持待看等補全文，全文 JD ⇒ `queued`（待評分）。JD 的「N 年以上」是下限，年資超出不扣分也不判不適合；只有 JD 明確設上限才可能 `fail`。
- **R3.5** 判定結果（逐條結論、命中的規則名稱、條件拆解）一律保存，供使用者理解「為什麼判不適合」與調整求職條件。
- **R3.6** partial 職缺（`discovered`，無 JD 全文）只套用欄位可用的結構化條件；需要內文或語意判斷的條件於補全文後執行——不以標題錯殺分類錯置的職缺。
- **R3.7** 結構化條件不耗用 LLM 且不需 JD 全文的特性，使它可作為**清單頁的快速判定**：插件收割列表項目時同步得出判定並回傳，供頁面就地標記（R9.1）。此路徑的延遲需求是「使用者仍在該頁面時看得到結果」，不等待任何 LLM 階段。

### R4 AI 軟規則評分（推不推薦）

只有通過硬規則篩選的職缺進入評分。評分只回答「推不推薦」，其輸入不含履歷敘事——`experiences` 的角色、成就與誠實邊界不進評分 prompt，避免「做過」被讀成「適合」。

- **R4.1** 四維評分（各 0–100）與權重：

| # | 維度 | 對照 JD | 權重 |
|---|---|---|---|
| 1 | 工作內容契合度（`content_fit`） | 工作內容描述 vs 想做／不想做的內容 | 50% |
| 2 | 待遇與制度契合度（`benefit_fit`） | 薪資、休假、獎金、遠端形式、工時制度 | 20% |
| 3 | 加分條件契合度（`bonus_fit`） | R3.3 拆解出的加分條件 vs 技能、證照、語言、產業經驗 | 15% |
| 4 | 產業契合度（`industry_fit`） | 公司產品／服務所屬領域 vs 期許產業 | 15% |

- **R4.2** 基準分制：各維度以門檻分為起點加減，clamp 0–100；無資訊可判時回基準分（中性）。`bonus_fit` **只加不減**——JD 的加分條件未滿足不得懲罰，否則列越多加分項的 JD 分數越低。
- **R4.3** 加權總分由程式計算（非 Agent 自算）；總分 ≥ **75** 進入 `shortlisted`，等待使用者決定是否要求生成求職信。
- **R4.4** 每筆評分附簡短「推薦/不推薦理由」，長度以中文一字、英文詞整段一字計。
- **R4.5** 篩選、評分、信件起草與信件審查可分別設定主要與備援 CLI Runner；使用者在本機調整設定後，下一輪執行即採用新路由。

### R5 雙 Agent 求職信管線（Drafter–Reviewer）

- **R5.0** **按需生成**：達閾值的推薦職缺（`shortlisted`）不自動進入求職信管線；使用者於 Side Panel 檢閱評分後，對想投遞的職缺按下「產生求職信」，Job 才轉入 `letter_requested` 由管線處理。理由：求職信是全流程最耗 token 的階段，且系統不支援自動投遞，未經使用者決定的求職信沒有使用價值。`letter_failed` 的職缺同樣由使用者再次要求才重跑。
- **R5.1** Drafter：比對 Profile 的 `experiences`（角色、組織類型、量化成就）、`qualifications` 與 `honesty_bounds` 與 JD 撰寫精煉求職信；強調量化實績；落款強制 `[你的姓名]`、`[你的聯絡方式]` 佔位符。
- **R5.2** Reviewer：審查草稿——凡 Profile 無根據的技能/經歷（幻覺）、過度空泛形容詞、誇大宣稱，判定 `revise`（附具體問題退回重寫）或直接刪改後 `approve`。
- **R5.3** 重寫上限 2 輪；仍不過審則標記 `letter_failed` 留待人工。
- **R5.4** 程式端防線：求職信中出現的技術詞須存在於 Profile 技能集（`qualifications.skills` ∪ 各 `experiences[].skills`）∪ JD 內文（詞表比對），落款佔位符缺失即擋下——不完全依賴 LLM 審查。

### R6 Chrome Side Panel 儀表板

- **R6.1** 職缺清單：按 Match Score 排序，可依 `process_state` / `apply_state` / 來源篩選；每筆顯示判定（不適合／推薦／不推薦／待看／待評分）。
- **R6.2** 「目前職缺」以窄幅單欄依序呈現判定、總分／篩選逐條結論、理由、四維評分、JD 內容與審查通過的求職信；判不適合者顯示未通過的條件，判待看者顯示缺少資訊的條件；尚未生成求職信的推薦職缺於此顯示生成入口。
- **R6.3** 一鍵複製求職信至剪貼簿。
- **R6.4** 投遞狀態變更（按鈕/下拉，MVP 不做拖曳看板），每次變更寫入 StatusEvent。
- **R6.5** 手動觸發一輪抓取與檢視 Run 歷史（含該輪職缺的現行判定分布）。
- **R6.6** Chrome 原生 Side Panel 是唯一日常操作入口，toolbar action 直接開啟；固定提供「目前職缺、待看、推薦、系統」四個頁籤。Options 可設定 localhost API endpoint 與 token。API 僅監聽 loopback；遠端部署時，extension 透過 SSH local forward 存取本機轉送埠。
- **R6.7** 待看頁籤列出 `discovered` 職缺（職稱、公司、薪資、原始連結），供使用者逐筆點開由 content script 補全文。
- **R6.8** 求職信生成入口：推薦職缺（`shortlisted`）提供「產生求職信」動作，送出後顯示處理中，完成時呈現求職信或未過審結果；`letter_failed` 提供再次生成。
- **R6.9** Side Panel 支援淺色與深色主題；切換不得清除目前頁籤、職缺或操作狀態。主題選擇可持久化，JD、求職信與 token 不因 UI 快取而另存副本。
- **R6.10** 「系統」頁依序呈現連線與設定、Profile、自動篩選與評分、自動與手動批次、批次歷程群組；可開啟 Options 與 Profile 全頁編輯器、開關自動篩選與評分、查看每日 08:30（Asia/Taipei）排程，並手動抓取或更新過時評分。Profile 編輯草稿只存在頁面記憶體；衝突時保留草稿並要求重新載入，不提供強制覆蓋。
- **R6.11** 職缺總分與四維分數在 UI 四捨五入為整數。已有評分的職缺顯示評分所屬 `score_revision`；與 active revision 相同顯示綠色「最新」，不同或無法證明則顯示黃色「待重評」。篩選結果同樣以 `filter_revision` 判斷是否過時。
- **R6.13** 自動處理開關與單筆立即處理：系統頁可開關自動篩選與評分（關閉時收集照常、職缺停在待篩選／待評分，求職信不受影響，用於暫停 token 消耗）；等待中的職缺於「目前職缺」提供「馬上處理」，立即處理該筆並插到自動處理佇列之前，不受開關與每日上限限制，呼叫照常計入用量。已有判定的職缺仍以「重新處理」表達異議。
- **R6.12** 重複職缺呈現：目前職缺列出同一群組其他來源的平台與連結，供使用者選擇投遞管道；評分與求職信只有一份。系統頁提供「疑似重複」清單，逐筆併排比較並由使用者裁決合併或忽略；已合併者可取消合併。

### R7 排程與執行

- **R7.0** 抓取與處理分別驅動：抓取（全自動來源爬取）由排程成批觸發；篩選→評分→生成由**常駐 worker** 持續消化資料庫中的待處理職缺。排程抓取、CLI 與插件擷取三個入口寫入的職缺共用同一條消化路徑，不因來源不同而有等待差異。
- **R7.1** `jobfinder run` 執行一輪抓取，抓完即退出，不等待任何 LLM 階段。全系統**冪等**：狀態即進度，中斷後重啟從殘留狀態續作，不重複計費已完成的 Agent 呼叫。
- **R7.2** 每日一輪抓取由 systemd user timer 觸發（台北時間）；Side Panel 與 CLI 皆可手動觸發抓取。worker 隨常駐服務啟動，無需觸發。
- **R7.3** LLM 呼叫序列化並套用最小間隔（rate limit），評分/生成筆數有**每日上限**（設定檔控制，台北時間日界重置）。上限用盡時職缺留待隔日，使用者的要求不會遺失。
- **R7.4** 自動處理可由使用者關閉（R6.13）：關閉時 worker 不再自動消化篩選與評分，收集與使用者已要求的求職信不受影響。使用者對單一職缺要求的立即處理不受此開關與每日上限限制，並優先於自動消化執行，至多等待當下一次 Agent 呼叫完成。

### R8 觀測與稽核

- **R8.1** 每輪 Run 記錄該次**抓取**的事實（時間、觸發方式、使用的搜尋條件、取得與新建筆數、錯誤摘要）。該輪職缺的判定分布於檢視時即時查詢導出，不存為抓取當下的快照——worker 非同步消化，快照必然過期。插件擷取的職缺由使用者自行導覽產生，不屬於任何 Run。
- **R8.2** Agent 原始輸入輸出留存（本地檔案或 DB），供除錯與作品集展示；內容不得含 PII。

### R9 瀏覽器插件（半被動擷取與即時判定）

本節的需求對所有半被動來源共用；目前為 104 與 Cake，新增平台即新增一組解析器與 URL pattern，需求本身不變。

- **R9.1** 列表收割與快速判定：於 104 搜尋結果頁／職缺通知頁與 Cake 搜尋／職類列表頁，自動擷取使用者已載入的職缺項目（職稱、公司、薪資、地區、連結）送 capture API。API 對每筆同步回傳判定，插件就地標記於該項目上：
  - **已存在於資料庫的職缺**直接回傳其現行判定與總分，不重跑任何階段——使用者一眼看出哪些已評為推薦或不適合。
  - **新職缺**入庫為 `discovered`，並以欄位可用的結構化硬規則（R3.6、R3.7）即時判定：命中淘汰規則者標記為**不適合**（`filtered_out`，紅底或排除圖示，附未通過的條件）；通過者標記為**待看**，成為待看清單成員。
  - 此路徑不呼叫 LLM、不算分數；清單欄位不足以支撐語意篩選與四維評分，強行判定既不準也拖慢回應。
- **R9.2** 內頁擷取與完整評估：於職缺內頁自動擷取 JD 全文送 capture API，建立完整 JD 資料並**同步**執行結構化硬規則比對，語意篩選與評分則交由常駐 worker 非同步進行（R7.0）。Side Panel 的「目前職缺」依此呈現：
  - 結構化硬規則淘汰者標記為**不適合**並附未通過的條件——該路徑不含 LLM，**同步即得**，不需等待。
  - 已有現行評分者直接顯示快取結果（判定、四維分數與理由），不重複計費。
  - 通過結構化條件者顯示**處理中**（語意篩選與評分），由 Side Panel 低頻輪詢本機 API 至結果出現；語意篩選判為待看時顯示缺少資訊的條件。使用者關閉分頁不影響後端消化，重開時直接命中快取。
  - 求職信不在此階段生成（R5.0）。
- **R9.3** 收割動線：使用者在各半被動平台自行設定搜尋條件並瀏覽結果，插件收割其瀏覽到的頁面；亦可於 104 註冊職缺通知，通知 email 僅作提醒，入口為站內通知頁（以 R9.1 收割）。
- **R9.4** 合規邊界：插件只處理使用者本人瀏覽器已載入的頁面；不背景開分頁、不批次自動抓取、不繞過任何防護。
- **R9.5** 待看清單消化：Side Panel 的待看頁籤提供逐筆開啟原始職缺的使用者動作。
- **R9.6** 判定用語一致：清單標記與 Side Panel 對同一筆 Job 顯示同一組判定，且由同一份 API 回應導出，不各自實作判定規則；跨平台亦一致，插件不因來源不同而改變呈現規則。
- **R9.7** 已合併職缺的判定沿用：收割或擷取命中 alias 時，回傳其群組 canonical 的判定與分數——在某平台看到的職缺若已由另一來源評過分，就地標記直接顯示既有結論，不重跑也不重複計費（R2.8）。

## 5. 完整流程

職缺有三條入口，匯流到同一套判定與同一個資料庫；求職信是所有入口之後、由使用者按需觸發的獨立階段。

Profile 是所有處理入口的共同前置條件。Profile 缺少或無效時，系統只提供 setup 與讀取功能；有效儲存後立即啟用新 snapshot，但不改動既有 Job revision。每個 filter／score／letter 工作開始時固定取得一份 snapshot 與 revision，工作途中不換版；既有職缺由使用者明確要求後才切換 revision 並重新處理。

```
【入口 A：批次抓取（systemd timer / Side Panel / CLI 觸發）】
  → fetch    ：全自動 Source（Yourator）抓取 → upsert Job（去重、變更偵測、跨來源分群）→ new
  → filter   ：硬規則篩選（程式比對結構化條件 ＋ Filter Agent 比對語意條件與條件拆解）
               → 任一 fail ⇒ filtered_out（不適合）
               → 僅有摘要且無 fail ⇒ discovered（待看，補全文後重判）
               → 全 pass ⇒ queued（待評分）
  → score    ：Scorer 四維評分 → 程式計算加權總分 → <75 ⇒ scored ∣ ≥75 ⇒ shortlisted

【入口 B：104／Cake 清單頁（使用者瀏覽 ＋ 插件，隨時發生）】  ※ 快速判定，不呼叫 LLM
  → 列表收割 ：搜尋頁/通知頁/職類頁 → capture API
               ├ 已存在於 DB ⇒ 直接回傳現行判定與總分（不重跑）
               ├ 命中其他來源的重複刊登 ⇒ 回傳 canonical 的既有判定
               └ 新職缺 ⇒ discovered → 欄位可用的結構化硬規則
                          → 命中 ⇒ filtered_out（不適合）∣ 通過 ⇒ 待看清單
  → 就地標記 ：不適合（紅底/圖示）∣ 推薦 ∣ 不推薦 ∣ 待看

【入口 C：104／Cake 職缺內頁（使用者點開）】                ※ 完整 JD ⇒ 完整判定
  → 內頁擷取 ：capture API → 補入 JD 全文（discovered ⇒ new，或新建 new）
  → 結構化硬規則 → filtered_out ∣ 排入篩選
  → 排入處理 ：通過者由常駐 worker 非同步跑語意篩選與評分
               → filtered_out ∣ <75 ⇒ scored ∣ ≥75 ⇒ shortlisted
  → Side Panel「目前職缺」：待處理時顯示處理中；完成後顯示四維分數與理由，或篩選未通過／缺少資訊的條件（已有現行評分則直接顯示快取）

【使用者於 Side Panel（推薦職缺的決策點）】
  → 檢閱清單與對照（判定、四維分數、理由、JD、篩選逐條結論）
  → 對想投遞的推薦職缺按「產生求職信」⇒ letter_requested
       → letter：Drafter 起草 → Reviewer 審查 →（≤2 輪重寫）
                 → 過審 ⇒ letter_ready ∣ 不過 ⇒ letter_failed（可再次要求）
  → 一鍵複製 → 外部平台手動投遞 → 標記 apply_state
```

## 6. MVP 不包含（Out of Scope）

- 104／1111 等反爬防護平台的伺服器端自動抓取，以及任何形式的反爬繞過（headless 瀏覽器偽裝、驗證碼破解、加密參數逆向）——不因技術可行而納入。
- 插件背景自動開分頁批次抓取。
- SMTP 寄信、求職平台自動填表/自動投遞。
- PDF 履歷排版與生成（以文字求職信輔助既有靜態履歷）。
- 多使用者、登入、收費、Landing page（保留為未來擴充）。
- 匯入 PDF／Word／Markdown 履歷並自動填寫 Profile、多 Profile／多履歷切換，以及可還原的 Profile 歷史版本。
- 以新 Profile 自動重生或覆蓋已核准求職信、改寫投遞狀態或投遞事件。
- 拖曳式看板 UI（以按鈕變更狀態替代）。
- 公司文化契合度評分（制度、管理方式、工作環境）與其所需的公司情報來源：JD 幾乎不揭露這類資訊，實作後只會恆回基準分，稀釋其他維度的區辨力。
